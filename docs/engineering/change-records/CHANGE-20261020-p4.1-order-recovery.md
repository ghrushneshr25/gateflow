# CHANGE-20261020 — P4.1 Order recovery correctness foundation

## Status

Implementation in progress → complete with verification section.

## Problem

Checkout is a linear synchronous orchestrator. Timeouts and lost responses leave orders stuck, may incorrectly `Fail` on transport errors, ignore admission consume errors, and do not resume on retry.

## Goals

- Resumable checkout using durable operation IDs
- Ambiguous outcomes ≠ failure
- Never CONFIRMED without inventory CONFIRMED
- Idempotent reconcile API
- Stable confirmation outbox event id per order

## State machine (Order.status)

| Status | Meaning | Hold | Next actions on Advance/Reconcile |
|---|---|---|---|
| CREATED | Order+hold created | HELD | Bind entitlement |
| ENTITLEMENT_BOUND | Bound | HELD | Reserve inventory |
| RESERVATION_HELD | Reservation known | HELD | Consume entitlement; start/lookup payment |
| PAYMENT_PENDING | Payment call ambiguous | HELD | Lookup payment by payment_operation_id |
| PAYMENT_SUCCEEDED | Payment SUCCEEDED | HELD | Confirm inventory |
| RECONCILIATION_REQUIRED | Needs operator/system drive | HELD | Same as Advance from evidence |
| CONFIRMED | Terminal success | COMMITTED | No-op |
| FAILED | Terminal definitive failure | RELEASED | No-op |

### Transitions

- CREATED → ENTITLEMENT_BOUND (bind OK)
- CREATED → FAILED (bind definitive fail)
- ENTITLEMENT_BOUND → RESERVATION_HELD (reserve OK)
- ENTITLEMENT_BOUND → FAILED (capacity/definitive reserve fail)
- RESERVATION_HELD → PAYMENT_PENDING (payment transport/ambiguous)
- RESERVATION_HELD → PAYMENT_SUCCEEDED (pay SUCCEEDED)
- RESERVATION_HELD → FAILED (pay FAILED definitive)
- PAYMENT_PENDING → PAYMENT_SUCCEEDED | stays PENDING | RECONCILIATION_REQUIRED
- PAYMENT_SUCCEEDED → CONFIRMED (inv CONFIRMED)
- PAYMENT_SUCCEEDED → RECONCILIATION_REQUIRED (inv expired/not confirmable)
- Any non-terminal → RECONCILIATION_REQUIRED when progress blocked but not failed

### Durable IDs

Assigned at CreateWithHold and never regenerated:
- `checkout_operation_id`, `inventory_operation_id`, `payment_operation_id`
- Confirmation outbox `event_id` = `evt_order_confirmed_<order_id>`

## Alternatives

- Return mid-state without resume — rejected (P4.0 audit)
- Temporal/workflow engine — out of scope
- Fail on any HTTP error — rejected (timeout ≠ failure)

## Non-goals (P4.2+)

Kafka publisher, Redis fence, full compensation/refund, delay payment scenarios beyond hooks needed for tests.

## Implementation summary

- `orchestrate.Driver.Advance` — shared resume/reconcile driver
- `orchestrate.HTTPDownstream` — S2S adapter; transport errors → `ErrAmbiguous`
- Checkout retries **resume** non-terminal orders
- `POST /v1/orders/{id}/reconcile` (buyer owner or `X-Ops-Role` / `X-Service-Name`)
- `GET /v1/admin/reconciliation` (ops/service principal)
- Stable outbox `event_id` = `evt_order_confirmed_<order_id>`
- Payment transport ambiguity → `PAYMENT_PENDING` (hold retained)
- Expired inventory → `RECONCILIATION_REQUIRED` (no confirm; compensation = P4.2)

## Limitations

- OS-level process kill not automated (durable mid-state resume tested instead)
- Full compensation workflow deferred to P4.2
- Kafka publisher still absent
- `idempotency_records` table still unused (orders table carries keys)
